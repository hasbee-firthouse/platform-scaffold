Honest scope — what this page is, and isn't

We would rather under-promise here and over-deliver in the repository. Three plain statements:

This page

A simulation, labeled as one

Every screen above is a front-end mock with canned data. No backend, no real sign-in, no email is sent. It exists to make the specification tangible in a pitch, nothing more.

The specification

The same path, running for real

SPEC.md commits the scaffold to run this exact path end-to-end — real Google OAuth, real invitation emails, PostgreSQL row-level isolation — and to prove it with an automated test that scripts this demo (§18.1, §22).

Deliberately deferred

Scope discipline, on purpose

Enterprise SSO/MFA, payment processing, and group-based access are designed-for but not built. Each enters when a real customer needs it — v1 ships the foundation every product needs on day one.

The fork economics

A product team forks the repository, edits one configuration file, and replaces one module directory. Everything on the left is inherited working code, never rebuilt.

Inherited when you fork

  • Sign-up, sign-in, sessions, account recovery (Google + email)
  • Organizations, invitations, member lifecycle
  • Roles & permissions, enforced server-side on every route
  • Tenant isolation — app-layer scoping plus row-level security
  • Per-tenant entitlements (the monetization hooks)
  • Audit log, admin settings screens, operator tooling
  • Theming & terminology from one config file
  • Email, background jobs, deploy image, CI, test harness

What a product team builds

  • Its own screens
  • Its own API routes
  • Its own permissions and roles, declared in a manifest

The task tracker in the demo above is the entire product-side build. That ratio — one thin module on a deep foundation — is the pitch.
